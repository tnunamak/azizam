### Deterministic job-notice rewrite
1. Before mount, freeze wall time at a literal NOW (e.g. epoch seconds 1,800,000,000). Old job remains created_at=1. Fresh jobs use the literal NOW for created_at and updated_at. Verify the actual freshness cutoff once production access exists; the exact boundary remains UNVERIFIED. Do not use Date.now twice around mount as a race-prone definition of “new.”
2. Keep polling progression explicit via awaited client.refetchQueries in act. Script each delta response independently by URL and phase; assert request sequence and committed watermark. Never let a default unmatched URL accidentally return a successful jobs response.
3. Replace getQueryData-only UI barriers with a settled initial fetch and committed rendered state. For beforePoll=false, await findByText('Video is ready') BEFORE markCreationOpened. For beforePoll=true or remount-negative assertions, await completed query work and flush its actual scheduled React notification/effects inside act before asserting absence. A synchronous query cache read alone cannot prove a negative. Do not add arbitrary sleep or increase timeout.
4. Keep same person/job/asset identity within each remount case; use distinct identities across unrelated tests if module state lacks a supported reset. Preserve alice→bob isolation in BOTH true/false parameter cases. Do not use resetModules casually if it produces two React copies. Inspect any module-level opened-creations/announcement registry before choosing a reset mechanism; that inspection is currently out of scope.
5. Unmount all views, cancel/clear each tracked QueryClient, drain only deliberately scheduled work, restore globals/spies/time and clear sessionStorage between cases. Ensure MutationObserver disconnects in finally. The same-node/zero-mutation test must actually flush the observer before reading records; “zero so far” before delivery is not proof.
6. Keep wall-clock-only freezing separate from timer virtualization. If fake timers also control React Query scheduling, configure userEvent advanceTimers and advance only intended known timers asynchronously within act. Do not run all timers against an infinite poll loop. The unit backoff table remains a pure test, not five real sleeps.
7. Additive tests may cover freshness cutoff ±1, successful multi-page watermark commit, duplicate completion response and unmount during a pending response, but those are explicitly new coverage. Do not report them as inherited old guarantees.

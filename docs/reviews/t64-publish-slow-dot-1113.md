# Publish-toggle critical path diagnosis

Pinned input: tnunamak/azizam at 2f6bcfeff3faa3cde47c605e196c819477860f78. Source-only review; no runtime profiling, tests, service calls, or product changes. Only this notes file is added.

## Finding and confidence

The strongest POST-latency suspect is the synchronous hot-reload callback `self._on_changed()`, documented as `reload_runtime_config`, while the store's RLock is still held. Confidence: 60%, a hypothesis, NOT a measured root cause. Its implementation and lock waits are outside the read allow-list. A full prospective snapshot is another concrete scaling cost, but blaming the store write alone is unsupported.

Crucially, “Saving publication…” does not prove the POST is still running. The UI keeps that label through a subsequent parallel list/detail refresh and waits for BOTH. A slow list can therefore keep the old button label after a successful POST and successful detail response.

Expect a narrow apply path to work because publication changes one workflow's run-control state, and the store already builds the validated prospective snapshot before commit. The likeliest wrong assumption is that the omitted reload callback has no additional consistency obligations; verify those before changing its contract.

## Work model

Let Wb be bundled workflows, Ws effective stored workflow records, S service records, M declared service model records, B total bindings across constructed workflow entries, I inline-template bytes, P distinct referenced template files, N total addressable names, and H this workflow's retained history count (normally <=20). D is whole registry document bytes. These are symbolic estimates, not fixture counts or measured timings. One stored registry document is not W SQL workflow rows.

## Ordered POST critical path

1. **Request scheduling and guard.** `gateway/workflow_owner_api.py:161-172` runs the injected guard in `asyncio.to_thread`, parses If-Match/body, creates Actor, then awaits a second thread-pool dispatch for the mutation. `:273-276` binds the publish route to store.set_published. Constant request/body work plus unmeasured executor queue wait and guard work. Guard implementation, session/database reads and associated locks are outside scope.

2. **Validation and shared lock.** `gateway/workflow_registry_store.py:412-415` validates boolean then calls _apply. `:543-550` takes the one store RLock before reading or building and keeps it through _publish/return at `:608-611`. Other mutations serialize; snapshot cache access also takes this lock (`:322-330`). Wait time grows with concurrent work, not directly row count; each holder's duration includes all work below, including hot reload.

3. **Read current document, then read it again for base snapshot.** `:546-550`, `:309-330`: _read invokes admin_store.get_service_registry_json_with_generation, parses the whole stored document; snapshot invokes _read again and release_digest before cache lookup. At least two document-read helper calls before mutation; O(D) parse work even on snapshot cache hit. Actual SQL row/query counts and release_digest caching are in excluded helpers. Cache miss also performs a full _snapshot_of build; hit reuses base.

4. **Build changed record, not just a SQL boolean update.** `:420-430` calls _effective_record; `:484-486` layers the ENTIRE document to select one workflow. `gateway/registry_layers.py:135-156` deep-copies stored data, traverses each collection and sorts record keys, applying patches. Cost grows with all registry collections (including workflows/services), approximately O(D + collection sorting). `workflow_registry_store.py:492-527` carries one owned contract or creates a small bundled run-control patch and increments record_revision. `:552-559` deep-copies stored document again, copies workflow map, and inserts the changed record; O(D+Ws). Calls to bundled_workflow_manifests/release_registry have out-of-scope cache/I/O behavior.

5. **Build the entire prospective snapshot before any registry commit.** `:560-570` calls _snapshot_of for generation+1; `:317-320` gets release, effective registry and injected _build. The documented builder is registry_snapshot.build. `gateway/registry_snapshot.py:525-577` constructs all Wb bundled entries and then all Ws stored/patched entries, including overwritten bundled entries; computes frontends/service model/dynamic alias names, collision checks, intent index and sorted snapshot digest. `:245-251` computes execution and record digests per constructed entry; `:218-226` computes binding digests and template refs; `:207-215` hashes/freezes inline templates every construction. Roughly 2(Wb+Ws) entry digests + B binding digests + inline-template digests + one snapshot digest (held-out fallback can add entries). Template path digest is LRU-cached (`:194-204`): up to P JSON file reads/parses/hashes on cold cache, zero on warm hits, eviction possible above 512 paths. Frontend YAML parses once per uncached (path,mtime,size) (`:176-188`); warm call still stats. All service model rows are traversed at `:375-390`; dynamic alias targets may rescan services/models via `:395-409,413-449`. Name collision normal path traverses N names; existing clashes cause repeated whole-name checks per owned workflow in `:480-515`, potentially much worse than linear. Exact name_clashes implementation excluded. No need to parse ALL historical revisions here.

6. **Stage one workflow's history.** `workflow_registry_store.py:571,654-673` reads holder SHAs, writes canonical bytes for one new history blob, obtains depth/config, then reads holder SHAs again and parses every held blob via `:640-648`, sorts by revision and keeps up to depth-1. Normal cost H blob reads/JSON parses + two holder enumerations + one new blob write; not all workflows' history. H normally <=20, but enumeration itself is not bounded before slicing if the holder is abnormal. Digest/SQL/fsync count inside DefinitionStore is unknown.

7. **Commit whole registry with audit and history-holder update.** `:572-591` calls admin_store.write_service_registry_with_audit with whole new_stored, expected generation, audit and history.apply callback. `:263-268` replaces the history holder inside this transaction; errors undo it (`:593-604`). Costs include whole document serialization/validation plus audit and holder update, but exact SQL, lock, busy timeout, hash and fsync operations are out of scope. Module contract `:3-18` explicitly describes document CAS, in-transaction name checking and two databases without shared transaction. Its workflow/service rereads, runtime rebuilding, I/O and locks are unknown; do not assert a specific reload query count. Listener count and bodies are also unknown. Callback failure raises RegistryNotApplied AFTER durable commit; listener exceptions are logged and remaining listeners continue.

9. **HTTP response.** `workflow_owner_api.py:190-196` returns 500 registry_not_applied with commit/ETag when hot apply fails, otherwise 200 with commit/ETag. Serialization is small. It does not return workflow detail/history or list in this POST.

## Smallest correct change proposal

First measure monotonic spans: executor queue, RLock wait/hold, current read, base/prospective snapshot, history, CAS commit, _on_changed, each listener, POST response, detail GET and list GET. Capture registry sizes and request/revision IDs, not secrets. Separate warm/cold and loaded-host samples. This distinguishes callback latency from post-response UI latency without guessing.

For POST cost, replace the broad no-argument callback on publication-only changes with a narrow generation-fenced apply of the ALREADY BUILT prospective snapshot. Proposed seams: constructor callback contract at store :292-300, _apply :610, and _publish :613-624. Pass old/new/commit and publish-change kind to the runtime apply function; update runtime provider plus required derived publication views synchronously, reject stale revision, preserve listeners and RegistryNotApplied semantics. Keep full reload fallback for other mutations. The actual callback implementation is outside scope, so exact main-gateway edit lines cannot be named and this is not an implementation-ready patch. Existing Provider.swap at registry_snapshot :609-612 is constant-time, but swapping only that object is NOT proven sufficient.

Do NOT simply return 200 after commit and schedule current reload in the background: current success means apply completed; 500 RegistryNotApplied cannot be delivered after the HTTP response. That alternative needs explicit saved/pending/applied revision state, durable retry/recovery and UI semantics, so it is not the smallest correctness-preserving fix.

For the confirmed UI coupling, a separate small change at owner-view :323-339 can apply awaited fresh DETAIL and clear pending without awaiting LIST, while refreshing list independently with a caught error and operation/alive guard. Keep next mutation disabled until detail supplies the new ETag. This removes unrelated list latency but does not repair a slow POST. Do not optimistically invert publication on commit alone or on registry_not_applied.

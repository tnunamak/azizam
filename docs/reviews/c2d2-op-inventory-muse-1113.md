## (g) What the tool cannot see

- Dynamic strings: f-strings, concatenation, .format(), and values built at runtime are not seen; only string constants are scanned.
- Unquoted TypeScript object keys (e.g. {chat: ...}) are not string literals, so they are not counted as occurrences or co-mappings.
- YAML/JSON values at keys outside the operation-like key set are not seeded, even when they name an operation (see Decisions in the notes).
- Words that appear only in comments, docstrings, tests, or docs are not counted as code occurrences (comments are skipped in the TS scan; docstrings are string constants, so a vocabulary word in a docstring does count).
- Closed sets spanning a call boundary (e.g. set(x) | set(y)) are not reconstructed; only one literal is reported.
- A vocabulary word used as a bare identifier (not a string literal) in Python is not a code occurrence; markers are the exception, because they are scanned textually.

## Decisions

- Final operation-like key set: `capabilities`, `capability`, `execution_intents`, `hidden_by`, `input_modalities`, `intent`, `intents`, `kind`, `media_type_modalities`, `modalities`, `modality`, `modality_words`, `operation`, `operations`, `output_modalities`, `policy_protocol`, `protocol_words`, `receipt_protocols`, `recommended_alias`, `route_intents`, `serves`, `shared_operations`, `task`, `tasks`, `type_capabilities`.
- `id` is recorded only when the row also carries an operation-like key, or the parent list is `capabilities`, `alias_operations`, or `rows`. Provider ids (providers/catalog), retention-fact ids, and other bare ids are not vocabulary. The rule still captures a few non-operation ids — frontend names (`openai`, `anthropic`, `ollama`), protocol names (`openai-compatible`, `chunked-stt`), and engine-definition metadata ids (`model_list`, `openapi`) — because their rows carry operation-like keys; they are visible in the table above, not silently filtered.
- Only `media_type_modalities` contributes vocabulary from a mapping value (MIME type -> modality word). A dict value at any other operation-like key (e.g. a JSON-schema object under `capability`) contributes nothing itself; nested operation keys inside it are still visited.
- `name` is recorded only inside `alias_operations` rows.
- `kind` is seeded as listed in the brief, but it is noisy: it also yields non-operation values (e.g. `field`, `json`, `template`, `none`). Those words stay in the vocabulary table so the noise is visible, not silently filtered.
- Bare `protocol` values (e.g. `openai-chat`) are not seeded: they name protocols, not operations. `policy_protocol` and `receipt_protocols` are seeded.
- Dotted workflow ids (e.g. `audio.generate.ace-step-1.5-xl-turbo`) are seeded whole; the pairs file connects them to their operation prefix via shared tokens.
- TypeScript is scanned with a character scanner (not a parser): string literals, bracket spans, and `if (...)` conditions. Enclosing function/class names there are approximate.
- Marker hits are textual: a line counts once per marker even if the marker appears twice on it. Endpoint markers match a full path segment, so `/view` does not match `/overview`.
- Engine names under `gateway/` are found by case-insensitive text search of non-Python data files; `llama` does not match inside `ollama`.

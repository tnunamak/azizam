# Azizam design principles (adopted; P11-P22 added 2026-10-11 from owner feedback)

Each principle comes from the owner's own words, quoted verbatim with its date. Each has a check, so it can be tested on a screenshot.

| # | Principle | Owner's words | Check on a screenshot |
|---|---|---|---|
| P1 | Every element pays for its attention. | "everything in the design that requires cognitive processing carries a cost" (2026-06-04) | For each visible element, name the decision or task it supports. Fail decorative facts with no use. Optional empty sections and quiet background watchers may be absent when no action or failure needs attention; required tasks, blocked actions and actionable failures must remain visible. Use P18 for data states. |
| P2 | One fact, one place. | "iI spent two seconds looking at the ui: this burns my attention by being repetitive" (2026-10-04) | Count facts visible together, including open disclosures, as one screen; test collapsed and expanded states separately. Repeat evidence only when it changes a decision. Navigation labels, repeated controls and identifiers needed to identify their local context may repeat. Fail two summaries of the same amount with no different use. |
| P3 | A failure names its layer and the next action. | "it's not clear if there is a gateway problem or a user problem or a model problem or workflow problem ... users shouldn't have this kind of trouble" (2026-10-02) | Errors expose a layer, public message, next action and optional Details. Use unknown when the layer is unproved. Member errors use plain words; developer API errors may retain required protocol fields. Pass: 'Gateway unavailable. Retry.' Fail: 'Invalid request.' 'Must be...' counts only when it tells the reader exactly what to change. |
| P4 | A family member understands it without help, on a phone. | "an experience my wife can understand and find delightful" (2026-06-14); "family members ... not a toy" (2026-10-03) | Record touch-only journeys at 390 CSS pixels wide: sign in, select a model, submit work, open a result and recover from failure. Require no help, horizontal scrolling or hover-only controls; targets are at least 44 by 44 CSS pixels. Truncate values to one line; keep task labels whole and full values one tap away. Apply P15; screenshots are required. |
| P5 | Complexity is navigable, not scary. | "a lot of complexity we need to make navigable and not scary and easy" (2026-10-03) | For each surface, name its main question and required tasks in the review. A named 390-pixel screenshot must answer that question in the first viewport; a recorded journey must reach each task and its details within one step of its relevant control. Fail hidden primary actions or unexplained choices. Source inspection alone is UNVERIFIED. |
| P6 | No marketing voice inside the product. | "we shouldn't have a big slogan like 'Build on AI in minutes'" (2026-06-25) | Read visible text in each named screenshot. Pass factual labels such as 'Create a key.' Fail slogans such as 'Build on AI in minutes' or unsupported praise such as 'effortless' and 'best.' Explain benefits only with specific, verifiable facts. |
| P7 | Honest data, rich wherever real data supports it. | "preserve the newer screenshots' contrast, density, hierarchy, charts-as-visual-pattern, and component language whenever real data supports them" (2026-07-16) | Trace displayed values and charts to real records. Missing amounts show unknown, not zero; zero requires a recorded zero. 'Local' requires execution-location evidence; 'no provider charge' requires billing evidence, not location alone. Fail invented sparklines or data-shaped decorative waveforms that imply measurements. Show units and missing samples. |
| P8 | Members are ordinary users; admins are users with an extra view. | "admins are users too right? don't apps usually have an admin nav from the normal user page" (2026-05-18) | Record the same named member journey in member and owner accounts at phone and desktop sizes. Pass when both use the same member shell and owner tools appear as an added section. Fail an owner-only replacement for ordinary member tasks. Backend text alone is UNVERIFIED. |
| P9 | Operators find it delightful too. | "r/selfhosted operators should find it delightful to use, too" (2026-05-17) | For each main surface, link a screenshot and journey showing one distinctive useful element and one response earned by a real action. Pass a readable live queue pattern and a completion confirmation after work finishes. Fail decorative novelty or celebration before success. Record reviewer acceptance; source inspection cannot certify delight. |
| P10 | Grounded in real references, not training data. | "pick some direction and then go find a bunch of references and ground the AI to those versus what's in its training data" (2026-08) | Each design change's review record links dated real references, the selected reference IDs and the resulting design choices or tokens. A principle or ban rule alone is not research. Approval must name the reviewer and reviewed version. Inspect that record, not just code comments; missing or inaccessible evidence is UNVERIFIED. Use P20 to check order. |
| P11 | Nothing legacy, in code, data, names or deployment. | "getting rid of any trace of anything legacy in the app and in my deployment with everything fully modernized" (2026-10-10); "I don't want legacy anything so why do we still have them vs mapping old keys to modern stuff?"; "this is unreleased" (2026-10-11) | Check code, records, configuration and deployment: only current identities remain, access meaning is preserved, obsolete apps/plans are gone. No shims, redirects or migration paths for Azizam's old URLs, formats or names. Exceptions: external OpenAI, Anthropic, Ollama, A1111 and MCP contracts, including boundary parsers and missing-data handling; clearly historical test fixtures cannot enable old product behavior. Renaming alone fails. |
| P12 | Engines, models, voices and workflows are data, everywhere. | "isn't the UI fully dynamic as the app is not supposed to have specific knowledge of any model or workflow or provider etc that must all be just data?" (2026-10-11) | Read identities and defaults for engines, models, providers, voices and workflows from editable service data. Core choices use declared capabilities, never engine names or aliases. Exceptions: stable protocol tokens, capability vocabulary, third-party setup/SDK examples and nondeployed test fixtures. Real names in data are valid; semantic test aliases must not create production branches or defaults. |
| P13 | Secure by default, as our own designs say. | "is None as an access plan supported by divan?"; "I don't want the default to be anything local in my own instance" (2026-10-11) | Test server denial for identities without an explicit access plan, including LAN authentication bypass. Link tests and the approved design for those scopes. UI selections cannot prove server enforcement; inaccessible core evidence is UNVERIFIED. Preserve access meaning when replacing identities. |
| P14 | Work the way real products work. | "Isn't the usual thing to have a self service link?"; "How does this relate to e.g. incognito which is how real products frame stuff like this" (2026-10-11) | Link prior art for each changed user-facing pattern from the change's review record. One component citation covers unchanged call sites using the same behavior; variants need their own rationale. For existing patterns, record the inspected scope and missing evidence as UNVERIFIED rather than assuming no research. Pass a linked recovery-flow comparison; fail an unsupported claim of standard practice. |
| P15 | Implementation details stay out of the interface. | "this playback text is weirdly placed"; "quality decisions is down" (2026-10-11); the Settings "identity rule / universal grant" copy (2026-10-11) | Normal views are member/owner screens before explicit technical disclosure. Ban internal IDs, service slugs, schema/policy terms ('identity rule', 'universal grant') and link lifetimes there. Use plain labels. Exceptions: copyable exact model IDs in the builder Models page and required developer API terms. Manage/receipt sheets count as Details only when explicitly labeled technical disclosures; opening any sheet is not enough. |
| P16 | One name per thing. | "is it confusing how models are mixed with model aliases"; "Why are there different model names?" (2026-10-11) | Use one canonical display name per model. Exact copyable IDs follow P15's builder/Details exception. Show separate choices only for measured differences in profiles or operations, and label those differences. Requested and served models may both appear when genuinely different and needed to explain routing or cost; fail duplicate aliases presented as different models. |
| P17 | Consistent across kinds of work. | "why does this only show on some types of generations?" (2026-10-11) | Record a matrix of options against supported generation kinds and declared capabilities. Offer each applicable option consistently. Show unavailable options with a visible reason, such as 'Voice selection needs audio output' or 'This provider does not support seeds.' Never silently hide an option because a capability differs. Fail inconsistent defaults for equivalent capabilities. |
| P18 | Every wait, list and notice has honest states. | "in Try I think there should be a loading state for models"; "Open result seems persistent even after I follow the link" (2026-10-11) | Test loading, unknown (unconfirmed), empty, ready (confirmed), malformed success, failure, media subfetches, refresh failure, changed inputs and reopened dialogs. Show freshness; mark stale data; reject stale responses; clear errors after success. Show percentages only when measured; otherwise phases. Lists state completeness; terminal events match records. Clear acted-on or invalidated notices. P1 permits quiet optional empties/background waits, not hidden actionable failures. |
| P19 | Keep valuable data; deletion is the owner's choice. | "if receipts are valuable data maybe we shouldn't burn them" (2026-10-11) | Keep receipts/history by default; prompt retention is separate. Deletion requires an owner-setting API, preview of affected records and owner approval before execution. Exclude active jobs. Document valuable records versus regenerable transport caches/spools; only the latter may expire without that approval. Test corruption recovery without silent record loss. Link server evidence; UI alone leaves retention and deletion behavior UNVERIFIED. |
| P20 | Research, full design and red-team before building. | "I don't want to design this on a whim I require the full design and grounded research inputs into the problem and only execution with very high confidence" (2026-10-11) | Before implementation, the change's review record must link dated research inputs, the full design and red-team findings with resolutions, plus a recorded go decision on the reviewed versions. References may include divan. Compare those timestamps with the first implementation commit; later comments cannot prove order. Missing dates, approvals or accessible records are UNVERIFIED. Audit existing work only within the declared scope. |
| P21 | Everything works headlessly through one core. | "the ui shouldn't be the only surface ... the entire system should be usable headlessly by design ... DRY as much as possible" (2026-10-11) | Keep a support matrix for every owner/member action: which surfaces (UI, REST, CLI, MCP) support it over one shared core rule, with tests; unsupported surfaces return an explicit error. Require CLI or MCP for automation, batch work, recovery and actions needed without a browser; document other omissions. Verify equal authorization, validation, outcomes and errors through server tests and live calls. Frontend API calls alone leave core/headless parity UNVERIFIED. |
| P22 | Extrapolate from feedback; do not wait to be told twice. | "I've given you a lot of feedback but it's not exhaustive. How can you properly extrapolate against it?" (2026-10-11) | Turn new feedback into a testable principle or refine an existing check, then sweep the product. Publish a coverage matrix naming inspected screens, journeys, viewport fixtures, core, shell, documents and deployment. Report every supported violation within that scope with evidence. Mark inaccessible or untested areas UNVERIFIED; never treat a scoped review as whole-product approval. |

# Azizam design principles (adopted; P11-P22 added 2026-10-11 from owner feedback)

Each principle comes from the owner's own words, quoted verbatim with its date. Each has a check, so it can be tested on a screenshot.

| # | Principle | Owner's words | Check on a screenshot |
|---|---|---|---|
| P1 | Every element pays for its attention. | "everything in the design that requires cognitive processing carries a cost" (2026-06-04) | For each element: what decision does it change? Remove it if none. |
| P2 | One fact, one place. | "iI spent two seconds looking at the ui: this burns my attention by being repetitive" (2026-10-04) | No repeated fact or sentence on a screen (lint plus a two-second look). |
| P3 | A failure names its layer and the next action. | "it's not clear if there is a gateway problem or a user problem or a model problem or workflow problem ... users shouldn't have this kind of trouble" (2026-10-02) | Every error state names the layer (or says it is unknown) and one action. |
| P4 | A family member understands it without help, on a phone. | "an experience my wife can understand and find delightful" (2026-06-14); "family members ... not a toy" (2026-10-03) | Member journeys pass at 390 px without help; no glossary-banned words. |
| P5 | Complexity is navigable, not scary. | "a lot of complexity we need to make navigable and not scary and easy" (2026-10-03) | The first viewport answers the surface's one question; detail is one step away. |
| P6 | No marketing voice inside the product. | "we shouldn't have a big slogan like 'Build on AI in minutes'" (2026-06-25) | No slogans or hype adjectives in product surfaces. |
| P7 | Honest data, rich wherever real data supports it. | "preserve the newer screenshots' contrast, density, hierarchy, charts-as-visual-pattern, and component language whenever real data supports them" (2026-07-16) | Charts, sparklines and KPI bands are allowed and encouraged on real data; nothing invented. |
| P8 | Members are ordinary users; admins are users with an extra view. | "admins are users too right? don't apps usually have an admin nav from the normal user page" (2026-05-18) | The member shell is the base; owner tools are an added section, not a different product. |
| P9 | Operators find it delightful too. | "r/selfhosted operators should find it delightful to use, too" (2026-05-17) | Each hero surface has one memorable element and one earned moment. |
| P10 | Grounded in real references, not training data. | "pick some direction and then go find a bunch of references and ground the AI to those versus what's in its training data" (2026-08) | Every design change cites a reference id, a token, a principle or a ban-list rule. |
| P11 | Nothing legacy, in code, data, names or deployment. | "getting rid of any trace of anything legacy in the app and in my deployment with everything fully modernized" (2026-10-10); "I don't want legacy anything so why do we still have them vs mapping old keys to modern stuff?"; "this is unreleased" (2026-10-11) | No "legacy" names in UI, data or config; old records are mapped to current concepts, not preserved under a legacy label; no leftover test apps or plans. Azizam is unreleased, so there are no compatibility redirects, shims or migration paths for its own old URLs, formats or names; only external client contracts (OpenAI, Anthropic, Ollama, A1111, MCP) are kept. |
| P12 | Engines, models, voices and workflows are data, everywhere. | "isn't the UI fully dynamic as the app is not supposed to have specific knowledge of any model or workflow or provider etc that must all be just data?" (2026-10-11) | No model, voice, provider or workflow names in UI or core code; defaults come from the service data the owner could edit. |
| P13 | Secure by default, as our own designs say. | "is None as an access plan supported by divan?"; "I don't want the default to be anything local in my own instance" (2026-10-11) | No option grants access without an explicit plan; defaults match the validated designs (deny by default). |
| P14 | Work the way real products work. | "Isn't the usual thing to have a self service link?"; "How does this relate to e.g. incognito which is how real products frame stuff like this" (2026-10-11) | Each user-facing pattern (sign-in, recovery, privacy, notices, pickers) cites the prior art it follows. |
| P15 | Implementation details stay out of the interface. | "this playback text is weirdly placed"; "quality decisions is down" (2026-10-11); the Settings "identity rule / universal grant" copy (2026-10-11) | No internal ids, lowercase service ids, link lifetimes, schema words or policy jargon in normal views; details live behind Details. |
| P16 | One name per thing. | "is it confusing how models are mixed with model aliases"; "Why are there different model names?" (2026-10-11) | A screen never shows two names for one thing; technical ids only in Details. |
| P17 | Consistent across kinds of work. | "why does this only show on some types of generations?" (2026-10-11) | Every option offered for one kind of generation is offered for all, or the screen says why not. |
| P18 | Every wait, list and notice has honest states. | "in Try I think there should be a loading state for models"; "Open result seems persistent even after I follow the link" (2026-10-11) | Loading, empty and error states exist; a notice clears once acted on. |
| P19 | Keep valuable data; deletion is the owner's choice. | "if receipts are valuable data maybe we shouldn't burn them" (2026-10-11) | No automatic deletion of history or records without an owner setting and a preview. |
| P20 | Research, full design and red-team before building. | "I don't want to design this on a whim I require the full design and grounded research inputs into the problem and only execution with very high confidence" (2026-10-11) | Every design change links its research (divan), design doc and red-team before implementation starts. |
| P21 | Everything works headlessly through one core. | "the ui shouldn't be the only surface ... the entire system should be usable headlessly by design ... DRY as much as possible" (2026-10-11) | Every owner and member action has an API (and MCP or CLI where it matters) using the same core rule as the UI. |
| P22 | Extrapolate from feedback; do not wait to be told twice. | "I've given you a lot of feedback but it's not exhaustive. How can you properly extrapolate against it?" (2026-10-11) | Each new piece of feedback becomes a principle with a check, and the whole product is swept against it. |

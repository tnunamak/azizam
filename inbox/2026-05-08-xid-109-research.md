# Xid 109 (CTX SWITCH TIMEOUT) Recovery Research — RTX 3090, Driver 595.71.05

**Date:** 2026-05-08
**Hardware target:** Dual RTX 3090 (Ampere/GA102), NVIDIA 595.71.05 proprietary, kernel 6.17, CUDA 13.2
**Triggering workload:** llama.cpp prefill on 50k+ tokens with mmproj image-encode; ComfyUI heavy generation

---

## Executive summary

**Reboot is *almost* the only reliable cure on consumer Ampere with driver 595.x.** The 595 branch has a *widely reported* Xid 109 regression vs. 590.x and 580.x that affects multiple GPU generations under heavy compute and Vulkan workloads [1][2][3][8]. NVIDIA's own catalog classifies the GPU as needing a reset action (RESET_GPU / RESTART_APP) once Xid 109 fires; for Ampere/Ada/Blackwell with GSP firmware, the reset path that actually works is the **PCI Secondary Bus Reset** on the upstream bridge — `nvidia-smi --gpu-reset` is deprecated since 570 and a plain sysfs `remove`/`reset` typically fails because GSP's WPR2 region remains locked [1].

**Best non-reboot recovery (load-bearing finding):** stop all GPU consumers, `echo 1 > /sys/bus/pci/devices/.../remove`, unload nvidia modules, then issue a Secondary Bus Reset via `setpci` on the upstream PCIe bridge, `echo 1 > /sys/bus/pci/rescan`, then `modprobe nvidia` [1]. This is documented end-to-end by another user against the same driver branch (590/595) and is the only software-only path that consistently clears the dirty GSP state.

**Best *prevention* shortlist** (most likely to reduce frequency before a reset is needed, ranked by evidence quality):
1. **Disable GSP firmware: `NVreg_EnableGpuFirmware=0`** in `/etc/modprobe.d/` (proprietary driver only — works on Ampere, no effect on the open kernel modules) [4][5][1].
2. **Downgrade to 580.159.03 LTS** — NVIDIA shipped 580.159.03 specifically as a maintenance branch for users who can't move to 595; one user confirmed Xid 109 disappeared after rebasing to a 580.x image on the *same hardware that crashed on 595* [3][6].
3. **`GGML_CUDA_DISABLE_GRAPHS=1`** for llama.cpp — known go-to for graph-related CUDA faults; documented as fixing CUDA-graph-induced crashes on multi-3090 inference [7].
4. **Lock clocks** with `nvidia-smi -lgc`/`-lmc` — primarily evidenced for *Xid 119* (GSP RPC timeout) caused by P-state transitions on Ampere [4]. Not directly proven against Xid 109; flagged as "plausible but uncited" for that specific Xid.
5. Reduce mmproj/long-context VRAM pressure — multiple llama.cpp issues confirm mmproj is *not* counted in `--fit` and silently causes pressure-induced failures [9][10].

**Honest verdict on "is reboot the only reliable cure":** No — Secondary Bus Reset *can* recover the GPU in-place [1]. But: (a) it requires killing every GPU consumer, including the X/Wayland session if that GPU drives display, (b) on a system where GPU0 hosts the desktop and GPU1 is the LLM card, you can scope the SBR to GPU1's bridge only, which is far more attractive than a reboot, and (c) once recovered, the underlying bug is unfixed — Xid 109 will recur. Disabling GSP and/or downgrading to 580 LTS is the only documented way to *prevent* recurrence on Ampere.

## 1. What NVIDIA officially says about Xid 109

NVIDIA's canonical Xid catalog (v590, current as of May 2026) describes resolution buckets — "Immediate Action" is intended as an automatable post-Xid recovery step, "Investigatory Action" is for persistent recurrence [11]. The actions are defined per-Xid and per-resolution-bucket on the "Fault Resolution Buckets" worksheet (referenced in the catalog HTML; the spreadsheet itself is at the `Xid-Catalog.xlsx` download link on that page). The HTML body does not contain the per-row text for code 109 — that lives in the downloadable XLSX. What is clear from the surrounding rows:

- Xid 8 (`ROBUST_CHANNEL_FIFO_ERROR_IDLE_TIMEOUT`, "GPU stopped processing") is bucket `RESTART_APP` for immediate, `CONTACT_SUPPORT` for investigatory [11]. Xid 8 is the channel error that *precedes* Xid 109 in the documented Ampere/Blackwell crash sequence [1].
- Xid 154 (`GPU recovery action changed to GPU Reset Required`) is the canonical signal that the GPU itself needs a reset, not just an app restart [1][11].

The relevant takeaway: NVIDIA documentation explicitly anticipates a reset bucket for this class of fault. There is no documented "soft" workaround in the Xid Errors deploy guide.

## 2. Per-mitigation breakdown

### 2.1 `nvidia-smi --gpu-reset`

- **Status:** Deprecated since driver 570 [1].
- **Evidence:** Multiple users on driver 580.105.08 report `nvidia-smi --gpu-reset -i N` returning "Unable to determine the device handle" once the GPU has hung [12].
- **Verdict:** Will not work for Xid 109 / GSP-locked state on consumer Ampere. Skip.

### 2.2 `echo 1 > /sys/bus/pci/devices/<bdf>/reset` (FLR via sysfs)

- **Status:** Documented to fail on Ampere when GSP's WPR2 region is still up [1].
- **Failure signature:** `NVRM: GPU0 _kgspBootGspRm: unexpected WPR2 already up, cannot proceed with booting GSP` on `modprobe nvidia` after the reset [1].
- **Verdict:** Doesn't clear the bad state; you'll fail to reload the driver. Not useful in isolation.

### 2.3 PCI Secondary Bus Reset on upstream bridge — **the load-bearing recovery**

- **Status:** Documented as the only working software-only recovery on driver 590.48.01 / 595.58.03 with GSP firmware [1].
- **Procedure** (from issue NVIDIA/open-gpu-kernel-modules#1080) [1]:

  ```bash
  # 1. Kill all GPU users (display server, llama-server, ComfyUI, persistenced)
  # 2. Remove the PCI device
  echo 1 > /sys/bus/pci/devices/0000:01:00.0/remove
  # 3. Unload all nvidia modules
  modprobe -r nvidia_drm nvidia_uvm nvidia_modeset nvidia
  # 4. Secondary Bus Reset on the upstream bridge (find via lspci -t)
  setpci -s 00:01.1 BRIDGE_CONTROL.w=0040:0040; sleep 1
  setpci -s 00:01.1 BRIDGE_CONTROL.w=0000:0040; sleep 3
  # 5. PCI rescan + reload modules
  echo 1 > /sys/bus/pci/rescan; sleep 3
  modprobe nvidia nvidia_modeset nvidia_drm nvidia_uvm
  ```

- **Risk profile:**
  - The **upstream bridge** for the GPU may be shared by *other* PCIe devices on the same root port. SBR resets every device behind that bridge — verify with `lspci -t` first.
  - Must **not** be run on the bridge of a GPU that is hosting the active display unless you're prepared to lose the session.
  - On the user's setup (GPU0 = display + ComfyUI/TTS, GPU1 = LLM only), this is workable for **GPU1** specifically without affecting the desktop, *provided* GPU1 sits behind its own root port — confirm with `lspci -t`.
- **Caveats:** Some users on consumer boards (Gigabyte MZ32-AR1, Asus boards, etc.) have reported PCIe ReBAR / IOMMU interactions causing reset failures [13][14].
- **Verdict:** Best non-reboot recovery option. Document the script, but practice it before relying on it.

### 2.4 Module reload alone (`rmmod nvidia_uvm nvidia_drm nvidia_modeset nvidia ; modprobe nvidia`)

- **Status:** Insufficient on its own when GSP has died — you'll re-hit the WPR2-up failure on `modprobe nvidia` [1].
- **Useful only as part of the full SBR sequence above.**
- **Pitfall:** `rmmod nvidia_uvm` can return "operation not permitted" if anything still has `/dev/nvidia*` open; check `lsof /dev/nvidia*` and `fuser -v /dev/nvidia*` first [generic NVIDIA troubleshooting; e.g., gpu-operator unload sequence].

### 2.5 `RmEngineContextSwitchTimeoutUs` (loosen the timeout)

- **Status:** **Tested and documented to have no effect** [1]. The reporter raised it from default 0x003fffff (~4.2s) to 0x01FFFFFF (~33.6s) and the bug still fired, confirming Xid 109 is a *symptom* of GSP heartbeat death, not a slow-context-switch root cause.
- **Verdict:** Don't bother.

### 2.6 `NVreg_EnableGpuFirmware=0` (disable GSP)

- **Status (Ampere proprietary):** Supported and documented to disable GSP on Turing/Ampere/Ada with the proprietary driver [4][5]. Not supported with `nvidia-open` (GSP is mandatory there).
- **Evidence:** Tencent Cloud's Xid troubleshooting guide and multiple long-running LLM training reports recommend it as a mitigation for GSP-related Xid families (119 explicitly; community reports extend to 13/79/109-class GSP failures) [4].
- **Trade-off:** Reverts to CPU-driven driver path; some loss of power management efficiency, possibly minor performance impact on workloads sensitive to driver overhead. Not load-bearing for inference.
- **How to apply:**
  ```bash
  echo "options nvidia NVreg_EnableGpuFirmware=0" | sudo tee /etc/modprobe.d/nvidia-gsp.conf
  sudo update-initramfs -u   # or dracut -f, depending on distro
  # Reboot or do the full module unload/reload ritual
  # Verify:
  nvidia-smi -q | grep -i gsp
  # Should show "GSP Firmware Version : N/A"
  ```
- **Caveat:** The user is on 595.71.05 proprietary, so this *is* available. Confirm the driver source is not `nvidia-open-dkms`.
- **Verdict:** **Strongest single prevention knob.** This addresses the documented root cause (GSP heartbeat death) directly. Recommended first preventive change.

### 2.7 Clock/power locking (`nvidia-smi -lgc`, `-lmc`, `-pl`, `-pm 1`)

- **Status:** Documented as effective for **Xid 119 (GSP RPC timeout)** caused by GPU dropping into low-clock states during P-state transitions [4]. The fix-pattern is `nvidia-smi -lgc 800,2100` and `nvidia-smi -lmc 800,10000` (locking a *minimum* clock to prevent the unstable transition).
- **Status against Xid 109 specifically:** **Not directly evidenced** in the threads reviewed. Forum-level mitigation reports for 109 focus on driver downgrade, not clock locking. No primary source ties power-limit reduction to Xid 109 frequency.
- **Persistence mode (`-pm 1`):** Web search returned **no documented evidence** that persistence mode resolves Xid 109; only general guidance that it stabilizes driver state at boot.
- **Verdict:** Worth trying as a *secondary* knob after GSP-disable. Low blast radius (fully reversible), low effort. Don't expect it as a primary fix.

### 2.8 Driver downgrade to 580.x LTS

- **Status:** NVIDIA officially shipped **580.159.03** on April 29, 2026 as a maintenance branch *specifically* for users who can't migrate to 595 [3].
- **Evidence:** A user on RTX 5060 Ti experienced Xid 109 on driver 595.45 reproducibly; rolling back to **580.95.05** (Bazzite NVIDIA-open image) resolved the bug entirely [6].
- **Caveat:** The user's hardware is Ampere (3090). 580.x supports Ampere fully. The user has stated they're locked at 595.x for unrelated bug-fix reasons in their stack — **this option requires that constraint to be re-evaluated**. If the 595-only fix is small enough to manually backport or replace, 580 LTS is the most evidence-supported clean fix.
- **Verdict:** If feasible, this has the strongest "before/after" evidence of any option here.

### 2.9 Workload knobs in llama.cpp / ComfyUI

- **`GGML_CUDA_DISABLE_GRAPHS=1`** [7]:
  - Documented to fix CUDA-graph-related crashes (RPC server graph leaks, K-cache quantization issues, unsupported DUP/CONT node types).
  - Performance cost: ~14% on H100 reference (143 → 163 t/s with graphs); on 3090 Q4_K_M inference the cost is similar order-of-magnitude.
  - Not specifically tied to Xid 109 in any cited issue, but it's the standard first-line workaround for graph-related CUDA faults.
- **`GGML_CUDA_ENABLE_UNIFIED_MEMORY=1`** — useful when VRAM pressure (mmproj on long context) is a factor [7].
- **mmproj is not counted in `--fit`** — confirmed bug, causes silent OOM in multimodal long-context [9][10]. Workarounds: manual `--fit` target reservation, or `--no-mmproj-offload` (vision encode goes to CPU; significantly slower for image-heavy workloads).
- **Reduce concurrent load on GPU0** (display + ComfyUI + TTS): not directly evidenced for Xid 109 on GPU1, but separating heavy compute from display-bound workload is a known stability practice on consumer cards.
- **Verdict:** Set `GGML_CUDA_DISABLE_GRAPHS=1` first; it's free to test and addresses a known class of crashes. Audit mmproj VRAM headroom on long-context runs.

### 2.10 Quiescent-period self-recovery (just wait)

- **Status:** **Not documented** in any reviewed source. Once GSP heartbeat dies, Xid 154 (`GPU Reset Required`) and watchdog messages indicate the device is in a non-recoverable state until reset [1]. The user's own experience that systemd-respawn within 30-60s leads to recurrence within minutes is consistent with: the first fault leaves the GPU partially compromised; subsequent runs hit the same wall faster.
- **Verdict:** Not viable. Do not expect quiescence to clear the state.

## 3. Driver-version specifics

- **595.x is widely reported as a regression** vs. 590.x and 580.x for Xid 109 across RTX 5060 Ti [6], RTX 5090 [1][2], and 30/40-series cards [8]. Both `595.45` and `595.58.03` reproduce the bug.
- **595.71.05** is documented in NVIDIA's data-center driver release notes [15] but does not list a Xid 109 fix in the changelog (release notes focus on Blackwell TMA descriptor / Xid 13 issues).
- **The regression chain:** First reported on the **575** branch (e.g., World of Warcraft Xid 109 regression vs. 570) [16], persisted through 580 stabilization, *worsened* on 595.
- **580.159.03 LTS** is the documented escape hatch [3]; **580.95.05** is community-confirmed clean for one Ampere/Ada user [6].

## 4. Workload-specific reports

- **llama.cpp / multimodal mmproj on 3090:** No primary issue thread directly ties Xid 109 to llama.cpp on a 3090. Closely related: [9] (mmproj OOM in `--fit`), [10] (mmproj loaded *after* fit estimation, no headroom), and a 3x3090/2x3090 CUDA error report on Qwen3.5-27B Q8 with `USE_GRAPHS=1` enabled [via search summary]. The pattern is consistent with VRAM-pressure-induced bus errors on consumer Ampere under graphs.
- **Long-context prefill (>32k tokens):** Reproduced indirectly through general "compute heavy AI stuff" Xid 109 reports on consumer Ampere [8]. The 50k+ token mmproj prefill workload is on the demanding edge of what 24 GB cards reliably tolerate.
- **Concurrent display + compute on consumer cards:** Multiple "GPU has fallen off the bus" Xid 79 reports on multi-3090 systems show that heavy concurrent load amplifies bus instability [12][13][14]. Separating LLM workload onto GPU1 is correct; the user is already doing this.

## 6. Honest caveats

- The strongest evidence base is for Xid 109 as a **GSP firmware heartbeat failure** that *manifests* as CTX SWITCH TIMEOUT [1]. Disabling GSP (#1) directly targets that root cause and is the single most likely preventive measure on Ampere proprietary.
- The user is on **driver 595.71.05** while documented Ampere SBR-recovery testing is on 590.48.01 / 595.58.03. The recovery procedure has not been confirmed against 595.71.05 specifically; the WPR2 lock pattern is unlikely to have changed within a point release, but it is not formally verified.
- The user's hardware mix is **GPU0 = display + ComfyUI + TTS, GPU1 = LLM**. SBR scoping requires confirmation that GPU1 is on its own root port. If GPU0 and GPU1 share an upstream bridge (common on consumer X570/X670/Z690 boards using a single CPU-attached x16 split into 8x8), SBR is **not viable without taking down the desktop**.
- **No documented setting reliably makes Xid 109 *not happen* on 595.x on Ampere.** Disabling GSP is the closest thing; downgrading to 580 LTS is the only confirmed clean fix.
